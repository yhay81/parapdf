# Reactで巨大なPDFを扱うとき、ページの仮想化と描画キャッシュを分ける

Reactで巨大なPDFを連続スクロールさせる場合、画面付近のページだけをマウントする仮想化が役に立ちます。ただし、マウントするページを減らすことと、描画のコストを管理することは別の問題です。

私はpdf.jsを使うReact向けPDFビューア、[ParaPDF](https://github.com/yhay81/parapdf)を開発しています。この記事では、その実装で分けて考えた「ページの生存期間」と「描画済みキャンバスの生存期間」を説明します。記事の執筆にはAIを利用し、ソースコードと記録済みの測定結果をもとに構成しています。

## 仮想化で減るものと、残るもの

[react-pdf](https://github.com/wojtekmaj/react-pdf)では、`Document`と`Page`でPDFのページを表示できます。巨大な文書については、[公式FAQも仮想化を勧めています](https://github.com/wojtekmaj/react-pdf/wiki/Frequently-Asked-Questions#rendering-pdf-is-too-slow-what-can-i-do)。react-windowと組み合わせれば、必要な範囲だけに`Page`を置けます。

一方、今回参照したreact-pdf 11.0.0は、[アンマウント時にキャンバスを解放します](https://github.com/wojtekmaj/react-pdf/blob/v11.0.0/packages/react-pdf/src/Page/Canvas.tsx)。そのページへ戻ると、描画済みのキャンバスは作り直しになります。PDFのデータがキャッシュされていることと、描いたピクセルが残っていることは別です。

画面外のページも多めにマウントしておけば、近いページへ戻るときの再描画を減らせます。ただし、その分のキャンバスを保持します。仮想化するページ数だけで、このトレードオフを調整するのは難しくなります。

## ページ数より、ピクセル数で予算を決める

キャンバスのRGBAデータを1ピクセル4バイトとすると、概算は次のようになります。

```ts
const canvasBytes = canvas.width * canvas.height * 4;
```

ここで使うのはCSS上の表示サイズではなく、キャンバス自体のピクセル数です。画面のdevicePixelRatioに合わせて描く場合、同じCSSサイズでもdevicePixelRatioが1から2になると、縦横それぞれのピクセル数が2倍になり、概算は4倍です。解像度を制限せずに倍率を2倍にする場合も、面積は4倍になります。

この概算はキャンバス分だけで、ブラウザ全体のメモリやGPUの追加領域までは表しません。それでも、「3ページだから軽い」と判断するより、保持量を制御する基準になります。

## Reactのツリーとキャンバスのキャッシュを分ける

ParaPDFでは、画面付近のページだけをマウントし、外れたページのキャンバスを上限付きのキャッシュへ移します。戻ってきたとき、キャッシュが残っていれば同じキャンバスを新しいページのホストへ移して再利用します。

役割は次のように分けています。

| 管理するもの | 判断すること |
| --- | --- |
| マウントするページの範囲 | 画面付近にどのページのホストが必要か |
| 描画済みキャンバスのキャッシュ | 戻ったときに使うピクセルをどれだけ残すか |
| 描画の優先順位と解像度 | 今見えている場所に、どの細かさの画像が必要か |

キャッシュは無制限に残しません。保持するピクセル数に上限を設け、全体の描画予算を圧迫するときは、画面外のキャッシュを先に解放します。[設計の判断と測定記録](https://github.com/yhay81/parapdf/blob/main/docs/decisions/0004-kept-canvases.md)も公開しています。

同様に、Reactの更新とピクセルの描画も分けています。スクロールやズームの各フレームではReactの状態を更新せず、マウント範囲や現在ページが変わるときにReactへ反映します。

## 汎用仮想リストと組み合わせる場合は座標の管理も必要

react-windowなどの汎用的な仮想リストで自前のビューアを組む場合、キャッシュを設けてもPDF向けの座標管理が別途必要になります。例えば、400ページ目の途中を拡大すると、ページの高さもリストの行の高さも変わります。倍率だけを更新しても、読んでいた箇所を画面に残せるとは限りません。

PDFのページ寸法、倍率、リスト上の位置を結び付け、ズーム前に見ていた文書内の点を基準にスクロール位置を補正します。画面外にあるページへの内部リンクも、移動先を仮想リストのスクロール操作につなぐ必要があります。

ParaPDFはreact-windowを使わず、こうしたページ配置・ズーム・移動・描画制御を一体で扱う実装例です。アプリ側ではツールバーなどの操作画面を作ります。[1,000ページのデモ](https://parapdf.yhay81.com/demo/?file=synthetic-text-1000.pdf)では、ページ移動やズームを操作できます。

## 更新回数が減っても、処理時間が短いとは限らない

2026年11月16日に、ParaPDF 0.9.0とreact-pdf 11.0.0 + react-window 2.5.3を比較しました。両方ともページを仮想化し、テキストとリンクのレイヤーを有効にしています。

以下は、1,000ページの生成文書の先頭から3,600 CSS px/秒で4秒間スクロールした条件の、各5回の中央値です。Apple M2 Pro・32 GiB、headless Chromium 158.0.8127.18、1280×900、devicePixelRatio 2で測定し、整数に丸めています。

| 指標 | ParaPDF | react-pdf + react-window |
| --- | ---: | ---: |
| スクロール中のReactコミット | 25回 | 43回 |
| 採取時点のキャンバス分の推定メモリ | 111 MiB | 249 MiB |
| スクロール中のメインスレッドのブロック時間 | 51 ms | 17 ms |

この条件ではReactの更新と保持ピクセル数は減っていますが、**ブロック時間はParaPDFのほうが長い**結果でした。

キャンバス分の値は、スクロール終了後に見えている空白が埋まった時点で採取した概算で、細部やDOMレイヤーの準備完了を待っていません。ブロック時間はスクロール中のタイマー遅延の合計で、停止後へ延期した処理を含みません。pdf.jsのバージョンも、ParaPDF側が6.5.438、react-pdf側が6.3.289と異なります。

また、このスクロール測定だけでは「戻ったページのキャッシュが何ms改善したか」は判断できません。戻る操作には別の測定が必要です。数値が示している範囲を分けることも、実装の役割を分けることと同じくらい大切です。[3ブラウザ・2文書・2速度の全結果と再現手順](https://github.com/yhay81/parapdf/blob/6ccee90f27095494bd9c441c2c3e846d45ddc86f/examples/prototype/results/compare-react-pdf-20261116.md)に、測定条件と制限をまとめています。Playwright WebKitはSafariそのものではありません。

## まとめ

巨大なPDFのビューアでは、マウントするページ数、保持するピクセル数、描画の優先順位を分けて考えると、それぞれのコストを調整しやすくなります。仮想化を導入した後も、再表示、ズーム時の座標、メモリの上限まで含めて設計する必要があります。

実装に関心があれば、[ParaPDFのソースコード](https://github.com/yhay81/parapdf)を参照してください。後で追いたいと思ったら、GitHubでスターを付けてもらえるとうれしいです。[Zennの記事](https://zenn.dev/yhay81/articles/202611-parapdf)では、導入方法とreact-pdfを組み合わせる際の実装負担をより広く紹介しています。
